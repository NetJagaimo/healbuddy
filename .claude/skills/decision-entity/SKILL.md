# 決策實體（Decision Entity）

本專案把每個決策視為一個「實體」，一個實體 = 一份 Markdown 筆記，存放在 Obsidian vault `docs/` 中。
目的：日後任何人（包括 Claude）都能回答「為什麼這樣做？」以及「改了這個會影響什麼？」。

## 什麼算一個實體

一個可以用名詞短語命名、且背後有「原因」的決定。例如：
- 技術選型：`PWA`、`Svelte`
- 產品範圍 / 行為：`離線使用`、`額外攝取記帳`
- 部署與流程：`github.io架站`、`前端測試`

判斷標準：如果未來有人可能問「當初為什麼選這個／為什麼不做那個」，它就是實體。
純實作細節（變數命名、某個 CSS 值）不是實體。

## 檔案規則

- 路徑：`docs/entities/<實體名稱>.md`
- 檔名即實體名稱，用使用者慣用的說法（中文或英文皆可），不加日期、不加編號。例：`離線使用.md`、`github.io架站.md`
- 檔名中避免 `[ ] # ^ | / \ :`，以免破壞 Obsidian 連結
- 建立前先 `ls docs/entities/` 檢查是否已有相同或近義的實體；有就更新，不要重複建立

## 筆記模板

```markdown
---
type: entity
status: 採用        # 採用 | 提案 | 待確認 | 棄用 | 已取代
date: YYYY-MM-DD    # 決策日期（絕對日期）
updated: YYYY-MM-DD
tags: [決策, <分類>]  # 分類：技術 | 產品 | 部署 | 流程
---

# <實體名稱>

## 決策
一兩句話講清楚「決定了什麼」。

## 原因
為什麼這樣決定。盡量保留使用者的原話與動機。

## 範圍與限制
這個決策「包含什麼、不包含什麼」，以及目前階段刻意不做的事（註明「現階段」）。

## 對實作的影響
這個決策帶來的具體要求，例如必須做的設定、不能用的技術、需要的測試。

## 考慮過的替代方案
- 方案 — 為何沒選（若無可省略此節）

## 相關實體
- [[實體A]] — 關係說明（依賴 / 支撐 / 限制 / 衝突 / 取代）
- [[實體B]] — 關係說明

## 變更紀錄
- YYYY-MM-DD 建立
```

## 連結規則

1. 一律用 Obsidian wikilink：`[[實體名稱]]`，不要用 `[文字](路徑.md)`。需要換顯示文字時用 `[[實體名稱|顯示文字]]`。
2. **雙向連結**：在 A 加入 `[[B]]` 時，也要到 B 的「相關實體」補上 `[[A]]` 與反向的關係說明。
3. 正文中第一次提到其他實體時就直接用 `[[ ]]` 包起來，不只寫在「相關實體」清單。
4. 可以先連到還不存在的實體（Obsidian 會顯示為未建立的連結），但要在回覆中告訴使用者，詢問是否建立。

## 索引與計劃書

- 每次新增、改名、改狀態後，更新 `docs/決策索引.md`：依分類列出 `[[實體]] — 一句話摘要 — 狀態`。
- 若決策影響 `docs/專案計劃書.md` 的內容，同步修改計劃書並在相關段落加上 `[[實體]]` 連結。

## 修改或推翻決策

- 不要刪除舊實體。把舊實體 `status` 改為 `已取代` 或 `棄用`，在「決策」下方加一行 `> 已被 [[新實體]] 取代（YYYY-MM-DD）`，並在變更紀錄寫明原因。
- 小幅修改（例如補充原因）直接更新內容，更新 `updated` 並在變更紀錄加一行。

## 流程

1. 從對話中萃取：決定了什麼、原因（引用使用者原話）、範圍、影響。
2. 缺少「原因」時，問使用者一句，不要自己編造原因；可暫時寫 `status: 待確認`。
3. 檢查既有實體 → 建立或更新筆記。
4. 補齊雙向連結。
5. 更新 `docs/決策索引.md`（以及必要時的計劃書）。
6. 回覆使用者：列出新增/修改的檔案與新增的連結。
